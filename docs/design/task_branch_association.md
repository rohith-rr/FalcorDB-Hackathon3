# Task-to-branch discovery from work periods and Clef

Status: proposed implementation addition. The workspace contains design documents, not runnable integration code. This specification extends [ingestion](phase_02_ingestion_and_sync.md), [model integration](phase_04_decision_model_integration.md), and [source adapters](source_adapters.md).

## Intended behavior and time evidence

When an assigned task is currently `IN_PROGRESS` and no confirmed branch association or precise task reference in available branch/commit/PR records identifies its implementation, discover likely branches using the assignee's commits during task work periods. Clef compares task purpose with branch activity to suggest associations even when task IDs are absent. Existing explicit mappings take precedence; conflicting explicit records remain conflicts rather than being overwritten by inference.

A work period is the intersection of an assignment interval for one person and a task `IN_PROGRESS` interval. Use half-open UTC intervals `[valid_from, valid_to)`; open periods end at the recorded observation time for inference. Reassignment, removal, completion, blocking and reopening split periods. Multiple assignees have separate person/work periods. Planned dates, task creation and generic `updated_at` are not transition timestamps.

Fetch paginated task activity history and reconstruct assignment/status intervals from native IDs and old/new values, checking against the current snapshot. Plane v1 supplies work-item activity records for this purpose. [Activity endpoint](https://developers.plane.so/api-reference/issue-activity/list-issue-activities), [activity fields](https://developers.plane.so/api-reference/issue-activity/overview). Preserve event IDs, effective/observed times and coverage; the activity actor is not automatically the assignee. Incomplete history cannot invent a start. Retained snapshots may establish an observed window only from the first observation onward, labeled `OBSERVED_BOUND`; a lone current snapshot supplies no historical window. Unexplained gaps make an interval partial, rather than proving continuous assignment/status.

An identity manifest maps tracker assignee IDs to native GitHub user IDs or explicitly verified Git author-email aliases. Match author identity rather than display-name similarity or the person who pushed/committed another person's work. Keep authored and committed timestamps separately; default matching uses authored time. Missing identity/time produces insufficient evidence. Co-authors need explicit normalized identity evidence; bots and merge-only activity do not establish the assignee's implementation.

## Retrieval and Clef decisions

1. Resolve allowed task/repository scope, current status and assignment. Return `NOT_APPLICABLE` for unassigned/non-in-progress tasks or an already resolved explicit association. Repository binding and identity mapping must be explicit.
2. Intersect reconstructed work periods with the last 14 days, configurable. Disclose excluded earlier history. No usable interval returns `INSUFFICIENT_EVIDENCE` without calling Clef. A bounded search never proves there is no branch outside its window.
3. Refresh repository refs and stable head. Inspect at most 20 non-stable live branches, 1,000 commits per branch and 100 changed file entries per qualifying commit, with overflow sentinels. Scope/candidate overflow requires narrower scope, not silent omission. Missing history/files/pages remain coverage gaps.
4. At each exact head, find reachable commits authored by a mapped assignee inside a matching period. Compare against the pinned stable head and distinguish inherited/shared commits from branch-specific work; reachability on many refs is not branch ownership. Retain messages, paths, bounded diff summaries, PR metadata and timestamps. Validate authored times locally rather than relying on a provider's date filter. Git exposes author/committer dates, and GitHub supports commit reads from a SHA/ref and changed-file retrieval. [Git log](https://git-scm.com/docs/git-log), [GitHub commits API](https://docs.github.com/en/rest/commits/commits).
5. Build authorized model state containing task purpose/acceptance criteria, work periods, overlapping tasks assigned to the same person, and candidate branch evidence. Paths/diff summaries help distinguish concurrent tasks. Do not send raw emails, unrelated tasks or inaccessible source text; missing competitor visibility is a limitation.
6. Supply at most 10 branch options per Clef request; more yields scope refinement and `INSUFFICIENT_EVIDENCE`. Use `choice` over exact option IDs plus `NONE`, `AMBIGUOUS` and `MULTIPLE`, with independent `noul` questions for each task/branch pair. Pair judgments preserve multiple associations rather than enforcing one task per branch. Same-request questions are independent. Default provider is `@cf/cloudflare/clef`, `model=clef`, through the existing adapter and server-side Cloudflare credentials. [Clef request contract](https://developers.cloudflare.com/workers-ai/models/clef/).
7. Validate option membership, finite probabilities and coverage. Initial configurable suggestion gates are pair probability at least 0.8; a single preferred branch also needs a choice probability margin of at least 0.15 over the runner-up. These are development defaults, not factual guarantees. `MULTIPLE` returns qualifying pairs; pair/choice disagreement, weak separation or unresolved competing-task matches returns `AMBIGUOUS`. `NONE` with no qualifying pairs is `NO_MATCH` within the searched window. Provider failure is `PROVIDER_UNAVAILABLE`; incomplete critical retrieval is `INSUFFICIENT_EVIDENCE`. Preserve evidence when abstaining.
8. Recheck task status/assignment, identity/mapping versions, graph generation and involved branch/stable heads after inference. Retry once after changes; otherwise withhold the preferred association and report stale/incomplete evidence. Persist suggestion records through the import protocol; the model has no graph-write permission.

Git commits do not record their original branch. Shared histories, rebases and cherry-picks remain ambiguous unless distinguishing evidence exists. Treat commit/source text as data, not model instructions. Temporal overlap does not prove every commit belongs to the task.

## Representation and use

The [contracts](contracts.md#task-branch-association) define `TaskWorkPeriod`, `IdentityBinding`, `BranchAssociationCandidate` and `BranchAssociationResult`. Retain activity/identity/model evidence, input/option hashes, model revision, scores, limitations and observed heads. Cache by task/period/identity/mapping versions, exact branch/stable SHAs, graph generation and model/question version.

Current suggestions use the configurable branch-evidence TTL (default 60 seconds), with `valid_until` bounded by the earliest required observation expiry. Refresh expired suggestions before describing them as current. The answer layer rechecks task/identity inputs and candidate/stable heads after its own LLM call; a failed check removes the preferred association and replaces current-association prose with deterministic uncertainty or explicitly historical observations.

An inferred association is `Task-[:IMPLEMENTED_IN]->Branch` with `link_method=INFERRED`, `authority=CANDIDATE` and an association/evidence reference. Task context renders a suggested implementation branch with person/time/content evidence and uncertainty. It cannot create `DELIVERED_BY`, confirm dependencies, change task status or establish verified branch-base coverage.

Promotion requires an explicit source-owned mapping or operator-authored manifest with actor/time/evidence. Selecting query clarification is a read preference, not promotion. Even a confirmed branch association needs complete delivery mappings, ancestry/reversion checks and final freshness checks before branch commands. Confirmed associations remain historical after completion; unconfirmed current suggestions expire or become historical when inputs change.

## Acceptance and evaluation

Generate real Git histories with synthetic task activities and mapped identities. Cover ID-free relevant work, same-person unrelated work in the same window, simultaneous similar tasks, multiple assignees/branches, reassignment/reopening, interval boundaries/time zones, missing history/identity, misleading messages, stable/shared commits, merge bots, author/committer disagreement, rebases/cherry-picks, deleted/force-pushed refs, overflow, malformed/timeout responses and task/head/generation changes while Clef runs.

Compare time/identity-only rules and Clef on identical candidates. Add at least 20 association examples including at least 10 held-out, grouped by scenario and separate from intent-routing counts. Measure candidate retrieval recall, suggested-pair precision, ambiguity/no-match correctness, multiple associations, ordering sensitivity, latency and cost. Tune thresholds only on development cases. The supervised demo gate requires no wrong accepted pairs in the controlled held-out set and at least 70% acceptance on its unambiguous positive cases; publish counts and the small-sample limitation. Failed/unavailable Clef stays disabled with visible evidence/abstention. Retain an actual Clef smoke result before claiming live inference.

Regression gates: high-scoring inferred edges stay candidates; inferred-only prerequisite coverage produces no verified delivery or branch command; explicit mappings keep precedence; task/repository/verified-base clarification and post-answer stale-narrative handling still pass. New work with confirmed no code prerequisites retains the existing verified-stable policy independently of discovery. These are future coding checks; this document does not claim runtime/model results.
