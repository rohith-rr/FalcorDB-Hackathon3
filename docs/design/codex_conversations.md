# Codex conversations as project knowledge

Status: proposed, 2026-10-09. User-requested addition to the Company Brain POC. No chat importer, extraction model, graph queries or UI have been implemented. This specification owns the JSONL adapter behavior; [schema](graph_schema.md), [contracts](contracts.md), [publication](graph_publication.md) and the coding phases consume it.

## Purpose and POC scope

Connect project discussions to the existing tasks, repositories, branches, commits, PRs, documents and services. Answer questions such as "Why did we choose this publication approach?", "Which conversations discussed this task?", and "Which alternatives were rejected or superseded?" Preserve the messages behind each answer instead of storing only a generated conversation summary.

The POC imports explicitly selected local Codex session JSONL files or saved exports for one configured project/repository. Use source mode IMPORT for real saved transcripts and FIXTURE for synthetic examples; a file watcher does not make historical messages LIVE operational evidence. Initial manual imports are sufficient. Incremental append handling is required for repeatable reimports; automatic watching/hooks are later convenience features. File access is read-only and imports do not modify Codex's own files or databases.

Codex's [official hook documentation](https://learn.chatgpt.com/docs/hooks#common-input-fields) exposes a nullable transcript path but explicitly states that the transcript format may change. The [CLI JSON event output](https://learn.chatgpt.com/docs/cli/reference) from `codex exec --json` is a separate source dialect. Do not assume these formats are identical. Record dialect, producer version when available, and parser version; verify real input shapes against sanitized fixtures before enabling a dialect. A local read-only inspection established that this project's current transcript has session metadata, message/tool response items, event records and runtime bookkeeping; this observation is not a universal schema guarantee.

## Source registration and normalization

Use the shared `SourceAdapter.read_scope(config) -> SourceReadResult`. Configure allowlisted files or a bounded source registry under allowlisted directories, explicit conversation-to-project/repository bindings, dialect, parser version, redaction policy and byte/record/message limits. Resolve paths and validate them against configured roots; query text and model output cannot choose arbitrary local files. Workspace metadata can suggest a binding, but a local cwd or Git ref alone cannot establish tenant identity, current branch state or permissions. Do not scan every personal conversation by default.

Normalize verified user-visible user and assistant messages, preserving source timestamp (nullable when absent), role, source sequence, message identity, content hash and capture reference. A `role=user` record can contain injected context or a relayed agent message; it does not automatically identify a human speaker. Supported parser fixtures classify message origin as HUMAN_INPUT, ASSISTANT_VISIBLE, INJECTED_CONTEXT or UNKNOWN. Import only verified conversational content by default. Preserve source speaker metadata with nullable verified principal mapping; never attribute a speaker from display-name similarity or from the operator who imports the file.

Exclude system/developer instructions, injected environment/context blocks, reasoning/encrypted reasoning, credentials, token counters and unrelated runtime records from retrievable content. Unknown origin is skipped with a coverage limitation. Optional selected tool receipts retain tool/call identity, sanitized arguments, recorded outcome and exact source reference; they are transcript observations, not authoritative GitHub/deployment records or proof that a test covered the claimed behavior. Attachment references may be retained as metadata; JSONL alone does not establish that image/audio/file bytes are available or that their contents were parsed.

Choose one canonical message representation per dialect. Local response items and event-completion/summary echoes must not create duplicate messages or repeated evidence. Preserve separate actual occurrences of identical text. Compaction summaries are derived historical context, never original utterances or replacements for unavailable supporting messages. Forks retain an explicit source-supported lineage and origin-message references when available; do not invent ancestry or count a copied prefix as new independent support.

## Capture, identity and publication

`Conversation` and `Message` have stable application IDs namespaced by tenant and Codex source instance. Use a verified source conversation/message ID when present. Otherwise use a retained source key and file epoch with source ordinal or pinned byte offset plus record hash. Renaming an allowlisted file can retain its registered source key; two conflicting logs with one claimed conversation ID require reconciliation, not silent merging. Message revision/content hash is separate from logical identity. Capture IDs identify immutable, sanitized content renditions with parser/redaction versions and an original captured-prefix hash; do not key every message by the changing whole-file hash.

Read a pinned prefix of complete JSONL lines. Defer an unfinished final line and report the pending tail; never advance the cursor past it. Invalid complete JSON, unsupported content-bearing record shapes or exceeded bounds block checkpoint advancement and report partial/failed coverage; explicitly recognized bookkeeping records may be skipped. COMPLETE means all eligible records in the declared captured prefix were handled, not that an active session has ended or that all past compacted messages are available. Preserve event time, capture observation time and ingestion time separately.

Stage a `ConversationImportCursor` with source key/epoch, complete-line offset, captured-prefix hash, last ordinal, parser/redaction versions and capture ID. Recheck prefix continuity on append; truncation, replaced files, changed historical bytes or parser/redaction changes require explicit reconciliation/full normalization. Missing/unreadable files do not prove conversation deletion. Version replaced captures and invalidate affected extracted decisions; an old ACCEPTED record cannot silently inherit revised rationale.

Conversation nodes, design decisions and their relationships belong to STRUCTURAL. Retain sanitized immutable captures, cursor records and operator reviews outside projection deletion. Reconcile the chat batch into the complete STRUCTURAL recovery bundle; preserve all other structural sources and INCIDENT links. Publish only through the existing single writer and durable protocol. Commit the published cursor only after STRUCTURAL READY, linking it to the published bundle; restart between publication and cursor acknowledgment reconciles that retained bundle before replay. No-op reimports do not create duplicate entities or change semantic inputs. Queries, answer generation and decision extraction never publish an import to save their own results.

The current two-projection design is retained. Manual chat batches may temporarily block structural readers. This addition does not create a third projection or rebuild STRUCTURAL after every appended line. Automatic batching can be evaluated later under the same ownership and access rules.

## Mentions, decisions and source authority

An exact scoped task ID, repository/PR URL, full commit SHA or version-bound document path can create a confirmed MENTIONS edge after resolving its existing authorized endpoint. Confirmation means the message references that entity; it never means the message's claim about the entity is true. Missing or ambiguous endpoints remain unresolved mention records. Semantic entity matches use INFERRED/CANDIDATE and cannot alter dependency, delivery, ownership or routing facts.

Store extracted proposals as `DesignDecision` records with PROPOSED status, supporting message IDs, rationale, alternatives, extractor/model/prompt versions and input hashes. A model may suggest acceptance or rejection, but cannot set ACCEPTED, REJECTED or SUPERSEDED. For the POC, a versioned operator-reviewed manifest records the exact decision revision, status, actor, review time and supporting messages. ACCEPTED establishes reviewed project intent only. SUPERSEDED requires an explicit replacement decision, review evidence and scoped ordering; reject self-links/cycles and conflicting accepted decisions rather than inventing precedence from the last chat timestamp.

Conversation facts are statements such as "the assistant proposed X" or "the reviewed design decision chose X". GitHub/Git still own PR state and revision coverage, task sources own status, and operational sources own deployments, responders and measurements. No chat or extracted decision can create confirmed DELIVERED_BY, task DEPENDS_ON, artifact provenance, incident-cause confirmation, action approval or a reusable permission grant. Imported messages are quoted data; instructions in them cannot authorize tools or override application policy. An execution approval must still use the exact current action-plan protocol.

To avoid circular evidence, record any original evidence references carried by generated answers. Repeated assistant statements or a summary repeating an earlier answer are not independent corroboration. References to a previous Company Brain answer retain that lineage; they cannot validate the original operational claim. Keep evaluator ground truth and branch-discovery instructions out of ingestion and extraction inputs. A known explicit chat reference to a task and branch must be disclosed in association evaluation; a case with that information is not an ID-free example.

## Retrieval, citations and access

Add CONVERSATION_CONTEXT intent and optional exact conversation/design-decision IDs to the canonical query contract. Task context can include linked discussion evidence; a project/repository-scoped rationale question need not resolve a task first. An ambiguous conversation/decision selection returns accessible bounded candidates in `ConversationContext` with no selected rationale, asking for narrower scope or a fresh exact-ID request; the existing TASK/REPOSITORY/BRANCH continuation variants are unchanged.

Provide bounded templates for conversation/message lookup, incoming MENTIONS for an existing entity, decision evidence, alternatives and supersession. Start with configurable caps of 20 conversations, 50 messages and 10 decisions per retrieval, plus a shared byte/token/depth limit and overflow sentinel. Exact links and heading/text search are sufficient initially; embeddings can rank permitted candidates but cannot confirm entity links or decision status. Retrieve supporting context, corrections and decision review/supersession state together. Trimming cannot hide qualifiers or turn a proposal into an accepted decision.

`ConversationContext` returns capture coverage, message excerpts, reviewed/proposed decisions, candidates and limitations separately from branch/incident `decision`. Cite conversation ID, capture/content hash, message ID, source locator, role and source time. Local `source_url` may be null; render a backend-controlled authorized transcript view instead of inventing a share URL or exposing an absolute machine path. `GET /conversations` lists scoped candidates; `GET /conversations/{conversation_id}/messages` requires an exact capture plus bounded message selection. Both use STRUCTURAL gates and current source/capture access checks; neither permits raw file reads or serves skipped/private fields.

Apply the existing source-access registry to registered transcript scope and captures before retrieval, model input, cached trace/view access and final publication. Explicit deny/exclusion immediately suppresses retained excerpts and derived decision rationale, including during a failed import. Imported content is not public just because its linked repository is public. Authoritative removal needs explicit evidence and a controlled tombstone/redaction update; already sent output cannot be retracted. Comprehensive retention/deletion policy remains Phase 7.

Read sets include exact capture/message hashes, permitted mention membership, negative searches, decision revision/review/status, supersession and coverage. Relevant corrections, new matching decisions or access changes invalidate prepared rationale; unrelated publications preserve equivalent answers. Appending a message during an answer does not automatically change every query, but a changed relevant result does. If a supporting message becomes unavailable, do not present an extracted summary as independently supported knowledge.

## Required implementation evidence

1. Import a sanitized fixture and one explicitly selected real project transcript. Reimport and append without duplication; preserve distinct repeated utterances and ignore event echoes. Record dialect/parser/producer version and original source times.
2. Exercise partial final lines, malformed complete records, unsupported shapes, null IDs/timestamps, injected user-role context, compaction, forks, missing attachments, renamed/truncated/replaced files and parser changes. Coverage and checkpoint behavior must match the rules above.
3. Link a real scoped task/PR/document reference and show its message citation; ambiguous/semantic mentions remain candidates. Retrieve a rationale, alternative and explicitly reviewed supersession without using evaluator answers.
4. Reject prose claiming a proposed decision was accepted, a chat-reported merge was verified, an assistant statement was a human approval, or a tool echo established recovery. Exact fact/citation IDs cannot bypass authority checks.
5. Import interruption and restart recover from retained bundles/captures; restart after publication/before cursor commit cannot lose or duplicate imported records. Chat imports preserve incident-owned records and existing live-adapter gates.
6. Denial during extraction/answer generation or failed import suppresses retained messages, rationale, transcript views and traces. Relevant message/decision changes invalidate output; unrelated publications reuse equivalent evidence.

These are future checks. JSONL ingestion does not satisfy the live Plane/Google Docs gate, the Clef discovery gate or sandbox-action evidence. The existing eighteen-task seed catalog stays unchanged; conversation work is mapped into the relevant coding phases without inventing source receipts or new external tasks.
